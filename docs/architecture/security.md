Mercato is a single-tenant C2C marketplace. Authentication and authorization are implemented with **ash_authentication** on the `users` resource. See the [ER diagram](../domain/entities.md) for `users`, `roles`, `permissions`, `role_permissions`, and `user_identities`; see [users.md](../domain/user/users.md) for the actual roles and account-status values and their business rules.

## Authentication

Sign-up and sign-in share the same three providers: **email + password, Google, Apple**. Each is an `ash_authentication` strategy — `Password` for email, `AshAuthentication.Strategy.OAuth2` for the two social providers.

- **Credential storage:** `user_identities` (one row per linked provider: `strategy`, `uid`, plus OAuth `access_token`/`access_token_expires_at`/`refresh_token`) — generated by ash_authentication's `AshAuthentication.UserIdentity` resource extension, unique on `[uid, strategy]`. A user can hold more than one linked identity; OAuth2 strategies auto-link a new identity to an existing `users` row when the provider's verified email matches.
- **Password strategy fields on `users`:** `ash_authentication`'s `Password` strategy keeps its own `hashed_password` and `confirmed_at` (email-confirmation add-on) directly on the `users` resource, not in `user_identities` — both the `Password` and `OAuth2` strategies read/write these same fields on `users` directly, since `hashed_password` must be nilable for OAuth-only accounts and OAuth sign-up stamps `confirmed_at` itself.
- **Phone verification (OTP):** a mandatory confirmation gate run once at sign-up, right after the primary method. On success `users.phone_verified_at` is stamped. Implemented as a custom add-on step layered on `ash_authentication`.
- **Web:** session-based cookie authentication.
- **Mobile:** API tokens / JWTs.
- **Nice-to-have:** magic link / SSO-code sign-in to reduce login friction.
- Sign-in is rejected for account statuses that block authentication (see [users.md](../domain/user/users.md#account-status)).

## Authorization

**RBAC:** `users` → `user_roles` → `roles` → `role_permissions` → `permissions`. A user holds one or more roles at once; `permissions` is data-driven, so each role is a `roles` row with its own `role_permissions` grants — adding a role doesn't require a schema change.

Authorization checks resolve against a session's **active role** only, never the union of a user's roles. The active role starts each session as the `user_roles` row flagged `is_default`, is switchable in-session to any other role the user holds with no re-authentication, and is not persisted — it reverts to the default role on the next login.

## Account Status

`users.status` gates authentication and available actions, independent of role. Implemented as a plain `status` attribute with Ash policies gating actions per state.
